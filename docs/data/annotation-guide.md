# 标注与复核规范 v1

先判断是否确实涉及公共交通服务体验。游戏、房源广告即使包含“地铁”也不能直接视为有效服务反馈；信息不足选 uncertain。随后独立判断情绪，记录事实且没有好恶为 neutral；同时有明确优缺点为 mixed；无关或无法判断为 unknown。不要将“人多”自动当成抱怨。

服务维度多选：拥挤客流、延误准点、设施设备、卫生环境、安检安全、票务支付、服务态度、线路换乘、舒适度噪音、无障碍。只选原文支持的维度；不要从“迟到”无条件推导全部延误成因。相关内容必须给出与原文一致的 evidence（start/end 为 Python 字符偏移，end 不包含）。

“传闻停运”可标事件候选，但 verification_status=unverified。帖子时间与事件时间分开；无法确定站名、线路或发生时间就保留未知。反讽、引用别人的意见、同一事件的矛盾叙述进入争议表，不能默认模型推断正确。

## 流程

1. 从 `prepare-review` 导出 pending 包，在本地保留；先确认近重复和同事件组。
2. 两位复核者独立标注首批约 40 条，记录原始分歧、裁决者和规则修订；没有第二位复核者时如实说明。
3. 逐条填写 analysis（符合 `Analysis` schema）、review_status=`human_accepted`、reviewer；analysis.label_source 必须为 human。AI 预标注只能作建议，未经逐条核验不称金标。
4. 记录数据/规范/切分哈希；开发集用于调整，测试集冻结。历史 XHS 全部排除盲测。
5. `evaluate --review` 运行多数类和仅在训练部分拟合词表的 TF-IDF centroid 基线。报告 Macro-F1、逐类支持数与混淆矩阵，不只报多数类准确率。

## 旧标签迁移

旧 C1–C9 是另一套任务定义。本轮没有可靠确认其全量语义，所以 `legacy-label-map.json` 明确保留 unresolved。先规范字符串前后空白/大小写，同时保留 original_label；0、空单元格、NaN 都属于未解释状态，不能据此判断无关。原预测字段永远不自动变为人工参考答案。

## 四个边界例子（合成说明）

| 文本 | 复核重点 |
| --- | --- |
| 今天地铁人多，记录一下。 | 可相关；中性描述不自动负面 |
| 换乘方便，但高峰拥挤得上不去。 | mixed；换乘与拥挤同时存在 |
| 网友说某线停运，我没看到公告。 | 事件候选；未证实；不补充真实城市 |
| 地铁跑酷新纪录。 | 游戏语境，无关；无服务维度 |
