# 项目讲解与两分钟演示

## 业务问题

过去的社媒满意度项目依赖脚本和历史标签，数字、情绪和热点容易混在一起。新版研究的是：使用者能否用一个问题调用可靠的统计与检索工具，并检查每条结论的来源，而不是仅收到一段流畅回答。

## 新版贡献与取舍

在保留旧团队资产的基础上，建立第一方 `metro_agent` 包、严格导入与证据 schema、LangGraph 受控循环、中文词法 RAG、SQLite checkpoint、费用预留、FastAPI 和 Web 工作台。开发使用 AI 辅助，不能称全部手写或发明 LangGraph。当前没有向量检索、多 Agent 或真实模型准确率证明。

数字由参数化 SQL 生成，报告引用工具结果而不接收模型新编的数字；原文引用从当前任务已观察集合中选择，并核对实际来源哈希和偏移。建议为未验证方案。这样牺牲部分自由叙事，换取可复查性。

## 演示顺序（约两分钟）

1. 运行 `uv run metro-agent serve`，指出 SYNTHETIC/离线策略标记；不冒充真实 LLM。
2. 点击“线路反馈”：观察 describe → aggregate → retrieve → finish；示例1号线有效反馈5条，其中negative 3、neutral 2，逐条核对原文。
3. 点击“无证据处理”：示例999号线返回无证据及零分母，不编造线路现状。
4. 点击“事件候选”：强调时间线以帖子发布时间排序，传闻没有被升级成事实。
5. 展示 CLI `--pause-after 2` 后 `resume`，成功工具不重跑；打开评测 JSON 和 GitHub CI。

## 两个能展开的案例

**故障恢复**：模型请求之前写 pending 和费用预留。如果服务端可能已计费但客户端没拿到结果，自动重试会隐藏重复计费风险。工程选择 needs_review；恢复必须明确接受风险。工具是只读操作，每步结果与游标一起提交，已完成工具不会重复执行。

**结论纠错**：Top-k 检索不是统计样本。把拥挤相关的两条原文当作全部反馈会高估负面占比；本项目用 aggregate 的全范围分母与 retrieve 的例证集合分别显示。传闻帖也只作为候选，不推断真实停运。
