# 接手后的初始架构决策

日期：2026-10-16。状态：默认实施基线，用户可调整；尚未实施。每条决策的成本与后续复核条件一并记录。

## ADR 001 采用受控Agent与LangGraph

背景：现有原型已使用LangGraph，但主要是固定分类流程；岗位样本更重视工具调用、评测和工程落地。

决策：保留LangGraph，构建有步骤上限的单Agent工具循环，把分析、统计、检索和报告校验作为明确工具/节点。

备选：全面多Agent系统、直接重建Dify应用。前者使成本和评测复杂度增加，后者更快但难突出代码贡献。

后果：运行时复杂度可控，但工具设计、独立评测与追踪必须自己做好。只有同一任务集显示单Agent受限时才引入专门协作Agent，不用数量衡量复杂度。

依据：[LangGraph](https://github.com/langchain-ai/langgraph)、[BettaFish源码](https://github.com/666ghj/BettaFish/blob/main/QueryEngine/agent.py)、[本地审查](../audit/2026-10-16-takeover.md)。

## ADR 002 新建src包并逐项迁移

背景：`platform`遮蔽标准库已实际复现，旧虚拟环境路径和依赖无法作为可复现规范。

决策：新代码进入`src/metro_agent/`，用Python 3.12作为初始兼容目标、uv管理与锁定依赖，旧目录先保留为只读参考，验证后再处理归档迁移。

备选：原目录原地修补、一次性搬走整个项目。前者保留包名风险，后者易破坏唯一历史资料。

后果：阶段性存在两套目录，需要明确README和入口；重建环境需验证LangGraph、模型适配器和数据库兼容性。不移动/删除旧原件来“清爽化”。

## ADR 003 数据优先离线导入

背景：已有大体量微博与80条小红书笔记，实时采集依赖登录态和图片URL时效。

决策：首版数据源为现存文件和授权导入，MediaCrawler作为外部可选适配器，演示无需浏览器登录。公开示例使用明确标注的合成数据。

备选：先修爬虫并常驻采集、复制第三方爬虫到新项目。它们不能直接补足Agent能力，也增加环境与许可成本。

后果：首版不能声称实时覆盖；现有小红书样本只能开发诊断，需额外未见样本验证跨平台泛化。

## ADR 004 使用正交标签与证据字段

背景：现有互斥四分类和“中性即负面”规则会丢信息，旧C1-C9与新版任务不同。

决策：相关性、情绪、服务维度、事件与事实核验分开，输出字段必须有支持片段；旧标签只经过显式映射进入新系统。

备选：保留四分类后继续调prompt。它容易维持旧界面，却无法消除定义层面的冲突。

后果：需要重建数据字典和部分人工标注，旧准确率不可沿用；指标更可解释，支持多维问题统计。

## ADR 005 结构化统计与检索分别承担职责

背景：报告需要正确数字和原文；Top-k检索无法代表整批数据。

决策：SQLite参数化统计提供数字，中文关键词检索作为基线，向量/混合检索经固定查询集验证后加入，报告按证据ID引用。

备选：直接把大量原文塞给LLM、直接上复杂向量数据库。前者成本和数字可靠性差，后者在小数据阶段未证明必要。

后果：需维护数据版本与索引同步；优先解释统计分母和检索质量，不宣称没有实测的RAG收益。

## ADR 006 本地trace与评测是核心交付

背景：旧项目结果缺调用、版本和独立金标链条；接入平台不能自动产生可信指标。

决策：本地结构化trace、固定测试集和人工复核为必选；Langfuse/Ragas等按实际接口和许可选择性使用。

备选：只做漂亮看板、只依赖LLM裁判、先部署完整观测平台。它们分别缺诊断、缺独立性或增加运维负担。

后果：初期更慢出漂亮Demo，但能解释失败、成本与改善。涉及公开或外发的数据继续脱敏，工具mock只验证工程行为。
